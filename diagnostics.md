# CloudDesk — отчёт по диагностике и отказоустойчивости

**Проект:** CloudDesk  
**Дата тестирования:** 23.11.2026  
**Среда:** GitHub Codespaces, Docker Compose  
**Технологии:** ASP.NET Core, PostgreSQL, Redis, CloudDeskWorker, Nginx

## 1. Цель работы

Проверить отказоустойчивость приложения CloudDesk при отключении отдельных сервисов, оценить поведение API и фонового обработчика, а также сравнить потребление ресурсов контейнерами до и после нагрузки.

В ходе работы были выполнены:

- Остановка и восстановление Redis.
- Остановка и восстановление PostgreSQL.
- Проверка HTTP-ответов и журналов контейнеров.
- Отправка 100 запросов к API.
- Сравнение использования CPU и оперативной памяти.

---

## 2. Проверка отказоустойчивости Redis

### 2.1. Остановка Redis

Для имитации сбоя выполнена команда:

```bash
docker compose stop redis
```

Контейнер `clouddesk-redis-1` успешно остановлен.

После остановки проверены маршруты:

```bash
curl -i http://localhost:8080/health/details
curl -i http://localhost:8080/api/stats
```

### 2.2. Результаты

| Маршрут           | HTTP-статус | Результат                             |
| ----------------- | ----------- | ------------------------------------- |
| `/health/details` | 200 OK      | PostgreSQL доступен, Redis недоступен |
| `/api/stats`      | 200 OK      | Статистика получена из PostgreSQL     |

Ответ `/health/details`:

```json
{
	"api": "ok",
	"postgresql": "ok",
	"redis": "error"
}
```

Ответ `/api/stats`:

```http
HTTP/1.1 200 OK
X-Cache: MISS
```

```json
{
	"total": 11,
	"newTickets": 7,
	"inProgress": 3,
	"done": 1
}
```

Заголовок `X-Cache: MISS` подтверждает, что статистика получена без использования кэша Redis.

### 2.3. Проверка Worker

В журнале фонового обработчика зафиксированы события:

```text
Worker connected to Redis
Processed: {"id":9,"operation":"created",...}
Processed: {"id":10,"operation":"created",...}
Processed: {"id":11,"operation":"created",...}
Processed: {"id":12,"operation":"created",...}
Redis unavailable: It was not possible to connect to the redis server(s).
```

При отключении Redis Worker зафиксировал ошибку подключения. В журнале также присутствуют записи об успешной обработке событий.

### 2.4. Восстановление

```bash
docker compose start redis
```

Контейнер Redis успешно запущен.

**Вывод:** отключение Redis не привело к отказу маршрута статистики. API продолжил получать данные из PostgreSQL, а маршрут диагностики корректно отобразил состояние Redis.

## 3. Проверка отказоустойчивости PostgreSQL

### 3.1. Остановка базы данных

Для имитации отказа PostgreSQL выполнена команда:

```bash
docker compose stop db
```

После остановки проверены маршруты:

```bash
curl -i http://localhost:8080/health
curl -i http://localhost:8080/health/details
curl -i http://localhost:8080/api/tickets
```

### 3.2. Результаты

| Маршрут           | HTTP-статус               | Результат                                 |
| ----------------- | ------------------------- | ----------------------------------------- |
| `/health`         | 503 Service Unavailable   | Проверка работоспособности БД не пройдена |
| `/health/details` | 200 OK                    | PostgreSQL недоступен, Redis доступен     |
| `/api/tickets`    | 500 Internal Server Error | Получение заявок завершилось ошибкой      |

Ответ `/health`:

```http
HTTP/1.1 503 Service Unavailable
```

```json
{
	"status": "error"
}
```

Ответ `/health/details`:

```json
{
	"api": "ok",
	"postgresql": "error",
	"redis": "ok"
}
```

Ответ `/api/tickets`:

```http
HTTP/1.1 500 Internal Server Error
Content-Length: 0
```

### 3.3. Журналы API

В журнале API обнаружена ошибка подключения к PostgreSQL:

```text
Npgsql.PoolingDataSource.RentAsync(...)
Npgsql.NpgsqlConnection.OpenAsync(...)
Program.cs:line 109
Program.cs:line 149
Microsoft.AspNetCore.Server.Kestrel...
```

Ошибка возникла при попытке выполнить запрос к остановленной базе данных.

### 3.4. Восстановление PostgreSQL

Выполнена команда:

```bash
docker compose start db
```

После запуска повторно проверен маршрут:

```bash
curl -i http://localhost:8080/health
```

Получен ответ:

```http
HTTP/1.1 200 OK
```

```json
{
	"status": "ok",
	"database": "connected"
}
```

**Вывод:** при остановке PostgreSQL операции получения заявок становятся недоступными. При этом API продолжает отвечать на диагностические запросы. После запуска PostgreSQL подключение восстановилось без изменения конфигурации приложения.

## 4. Нагрузочное тестирование

### 4.1. Методика

Для оценки потребления ресурсов использовалась команда:

```bash
docker stats --no-stream
```

Затем отправлены 100 последовательных HTTP-запросов:

```bash
for i in $(seq 1 100); do
    curl -s http://localhost:8080/api/stats > /dev/null
done
```

После завершения серии выполнен повторный замер.

### 4.2. Использование оперативной памяти

| Контейнер  |     До нагрузки |  После нагрузки |      Изменение |
| ---------- | --------------: | --------------: | -------------: |
| Nginx      |       10.53 MiB |       10.55 MiB |      +0.02 MiB |
| API        |       79.38 MiB |       77.44 MiB |      −1.94 MiB |
| Worker     |       18.91 MiB |       18.91 MiB |          0 MiB |
| PostgreSQL |       22.43 MiB |       23.91 MiB |      +1.48 MiB |
| Redis      |       4.605 MiB |       4.617 MiB |     +0.012 MiB |
| **Всего**  | **135.855 MiB** | **135.535 MiB** | **−0.320 MiB** |

По результатам замеров общее использование оперативной памяти практически не изменилось.

### 4.3. Использование процессора

| Контейнер  | CPU до нагрузки | CPU после нагрузки |
| ---------- | --------------: | -----------------: |
| Nginx      |           0.00% |              0.00% |
| API        |           0.04% |              0.04% |
| Worker     |           0.18% |              0.21% |
| PostgreSQL |           0.01% |              0.01% |
| Redis      |           0.49% |              0.50% |

После завершения запросов существенного изменения загрузки процессора не наблюдалось.

### 4.4. Анализ результатов

- Все пять контейнеров продолжили работать после серии запросов.
- Использование оперативной памяти оставалось примерно на уровне 135–136 MiB.
- Загрузка CPU в двух замерах была низкой.
- Заметного увеличения потребления ресурсов после серии запросов не обнаружено.

**Примечание:** замеры выполнялись до и после нагрузки, поэтому полученные значения не отражают максимальное потребление ресурсов непосредственно во время выполнения запросов.

## 6. Общий вывод

В ходе работы была проведена диагностика приложения CloudDesk при искусственных отказах Redis и PostgreSQL.

Установлено, что при недоступности Redis маршрут `/api/stats` продолжает работать за счёт обращения к PostgreSQL. Фоновый обработчик фиксирует ошибки подключения к Redis.

При остановке PostgreSQL маршруты, зависящие от базы данных, перестают работать, однако диагностические маршруты продолжают отвечать и отображают состояние зависимостей. После восстановления базы данных API снова успешно проходит проверку `/health`.

Серия из 100 HTTP-запросов не привела к заметному изменению потребления оперативной памяти после завершения нагрузки.

Таким образом, приложение обеспечивает частичную отказоустойчивость при сбоях Redis, корректно диагностирует недоступность зависимостей и восстанавливает работу после их повторного запуска.
